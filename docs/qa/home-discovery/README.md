# Balanced homepage discovery

The homepage targets two equal discovery halves: 12 songs and 4 playlists for
the user's taste, followed by 12 songs and 4 different playlists to explore.
Actual counts depend on available playable results; exhausted pools can reuse
previous impressions instead of inventing tracks or filling the page with copies.

## Selection

- Saved genres and followed artists (including channel metadata) lead the taste
  half. Seeds rotate within those families, with up to two familiar searches.
- Without those preferences, the newest searches and recent listening provide
  seeds. Private sessions ignore both activity sources. Accounts with no usable
  signals and guests get a popular-music starting point.
- Exploration uses related subgenres from the existing taxonomy and searches for
  similar artists/music. It first requests uploads published in the last 180 days;
  if those are unavailable it falls back to related music labeled "New to you".
  Known favorite artists and the current artist seed are excluded from exploration
  candidates. This is query-based discovery, not a trained similarity model.
- Each half fetches playlists using its own seeds. Track selection alternates
  between both pools so one side cannot consume all shared results. Playlists
  deduplicate by provider ID and normalized title across both halves.
- Recently played recordings, skipped/hidden/snoozed IDs, and explicit-content
  restrictions remain excluded. Cached provider candidates are reused; final
  personalized responses are private/no-store.

## Whole-page repetition audit and changes

Quick Access previously repeated history and recommendations shown lower down.
The generic category/mood rails were labeled as personalized but ignored the
account, and the featured-release fallback could label an arbitrary song as new.

The homepage now uses one composition step for Quick Access, the remaining history,
followed releases, and both discovery halves. It deduplicates track IDs and
canonical recording identities globally. Followed releases contribute to the
taste half; they are not displayed again in a featured card or another rail.
The two curated halves replace the static category/mood and overlapping genre
rows. Mix browsing remains available at `/mix`.

Refresh favors unseen songs and playlists. The existing account-scoped session
cache retains at most 96 displayed video IDs and 24 playlist IDs for up to 24 hours.
Private sessions neither read nor write those impressions. Sign-out cleanup
removes the existing cache namespace. No recommendation profile writes are added.

## Verification

`node docs/qa/home-discovery/check.cjs /tmp/haykasa-home-fixtures.json` executes the
real API handler, selection/composition utilities, and feed hook with synthetic
account/provider boundaries. It covers taste/activity precedence, related genres,
fresh-publication requests, metadata-only artists, empty/private accounts,
balanced counts, whole-page recording/playlist uniqueness, cached candidates,
feedback/history exclusions, bounded IDs, refresh, and account/private storage.

`node docs/qa/home-discovery/browser.cjs /tmp/haykasa-home-fixtures.json` starts
the real Next.js app and runs desktop/mobile Chromium across seven account
scenarios. API fixtures are generated by the real handler above. The browser checks
the entire homepage DOM for duplicate recordings, IDs, and playlists, horizontal
overflow, both discovery halves, correct fallback copy, Refresh requests, and UI
exceptions. External network traffic is blocked. Screenshots and results are
uploaded by `.github/workflows/home-discovery-vm.yml`.

These are controlled VM checks, not an authenticated live-catalog test. Vercel
preview has no MongoDB connection (`MONGODB_URL` is production-only), so its
persistent rate limiter prevents live discovery verification until preview has
its own database. Production data is not copied into the VM or previews.
