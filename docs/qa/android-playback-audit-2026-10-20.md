The user tested the APK offered by **Download for Android** in Settings. That public release is the PR35 build (`2279fffe`), with SHA-256 `40076622cae6a5049fbcb2c9449964d42915179e1ada0d8e6aa02a863b26a1c9`. It does not include the later asynchronous-playback, crash-recovery, viewport and update fixes. This audit tests the current PR39 Android 1.0.2 / version code 3 separately from that download.

Fresh browser profiles remain guests with no authentication cookie. Seeding an old account's local caches or persisted preference owner does not authenticate or expose that account. The APK WebView, Electron profile and Chrome have separate cookie stores. A browser-installed PWA shares its browser's storage. Existing native cookies can survive updates; the desktop profile is intentionally retained across reinstalls. No shipped credentials or automatic account creation/login were found. The reported first-ever login on the dummy phone remains unreproduced, so persisted cookies are a possible explanation, not a proven diagnosis of that device.

The media resolver is selected only when the mobile session is eligible and source playback is enabled. Capability responses now retain `enabled` and add a coarse reason: `mobile_only`, `service_unconfigured`, `service_disabled`, `authentication_required`, or `service_unavailable`. They never prepare a source, return configuration/secrets, or authorize a guest.

Backend tests passed actual FFmpeg remux/codec verification and decoding of synthetic AAC/MP4 and Opus/WebM, signed delivery/ranges, and 93 media fuzz cases. Those tests mock provider acquisition. The prior hosted live extraction returned `source_access_restricted`; a local live retry encountered an outbound-proxy tunnel rejection before reaching YouTube. Neither result establishes a playable real asset. Production source playback was not enabled as a workaround.

Current source passes lint, type checks and production build; fresh/revoked-session, SDK recovery, Skip/provider-error, capability, native unit/lint and APK/instrumentation compilation checks. Browser fixtures use isolated APIs and synthetic provider code, explicitly marked in their result files. They do not prove that a real YouTube song produced audio.

The first Android 13/16 run used the latest APK with the deployed website. Android 13 reproduced the recovery loop above; Android 16 exposed a missing-probe-schema error in the new QA code. The loop was an application failure, while the null-pointer error was in the instrumentation. Probe installation now runs at document start and after settled search results, checks schema explicitly and preserves diagnostic evidence instead of inferring a result. Initial tour screenshots/JSON were also missing because `UiAutomation.executeShellCommand` does not parse shell pipelines/redirection. Evidence writers now use a trusted shell stdin script and read back JSON/PNG bytes, and the runner fails when required evidence is absent.

The repeat run tests the current PR's compiled production web UI through an `androidTest`-only loopback interceptor. Public APIs and YouTube requests remain live, while the distributed APK's origin, network permissions and native bridge policy remain unchanged. HTML-delivery counters verify that the current build was used. This is staging verification, not evidence that the unmerged web changes are deployed. The test does not write accounts, history or playlists.

The Android 13 and 16 runs execute a settled-screen guest tour and a real-song tap probe, collect screenshots, fixed console/network categories and playback JSON, and separately require decoded native buffers with nonzero player volume. The emulator host uses `-noaudio`: playback progression/output settings and decoder counters can be checked, but physical-speaker audibility cannot be claimed. A passing failure-state check means the error is handled correctly; it does not mean the song played.

The guest media capability returned `enabled: false`; YouTube rejected both embeds. Native decoding passed with a controlled synthetic source, not a live yt-dlp asset. A real permitted source must resolve, download and decode successfully from the intended host before enabling source playback. Physical-device speaker/background playback and authenticated live extraction remain unverified.

**Delivery:** PR39 remains unmerged. The Settings download still points to the older public APK until a verified main build publishes a versioned preview. Both the web deployment and a new installed native build are required for the complete repair; debug previews do not receive automatic Play updates. Play distribution additionally needs maintained signing credentials and an approved listing/test track.
